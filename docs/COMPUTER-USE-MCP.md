# Computer Use: MCP server

**Status:** Experimental. Not yet run on a real Mac. Off by default; LAN mode needs TLS and a key.

The Core (everything that does not touch macOS) is covered by `swift test`, which runs in CI on Linux and macOS. The macOS layer (sockets, TLS, permissions, screenshots, input, settings page) has only been compiled in CI, never run on a real Mac. Read [Not verified yet](#not-verified-yet) before relying on any of it.

## What it is
Computer Use is a gadget of Nacho Combo. When it is on, it opens a **Streamable HTTP MCP server** on this Mac (`http://127.0.0.1:47653/mcp`). An MCP client that holds an API key (Bearer) can then call tools to look at the screen and to control apps, windows, input and the clipboard. When the gadget is off, the port is closed and every connection, the emergency-stop shortcut and any running shell command are cleaned up (the OFF contract).

In the app:
- It has its own page in the settings window (sidebar ▸ Computer Use) with a header switch, like every other gadget. All tool groups on that page are off by default.
- It is **excluded from combos**: a combo never switches it on or off, and it is not part of a combo's gadget list. It is only ever turned on by its own switch.
- Its emergency stop `⌃⌥⌘.` is **reserved**: no other shortcut in the app can take it.
- Its settings are stored in `~/Library/Application Support/NachoCombo/settings.json` under the key `computerUse` (port, listen mode, tool-group switches, extra allowed host names). A missing or broken section loads as the defaults, which means everything off. API keys are not in this file (see [API keys](#api-keys)).

## Structure
| Layer | Files | Tested by |
|---|---|---|
| Core (Foundation only, runs on Linux) | `Sources/NachoComboCore/ComputerUse*.swift` | `swift test` (Linux and macOS CI) |
| macOS | `Sources/NachoCombo/ComputerUse*.swift` | compiled in CI only; **not run** |

Core: SHA-256 and constant-time comparison, API key store, rate limits, JSON-RPC 2.0, settings (tool-group switches, loopback enforcement), tool catalog, policies for arguments, paths, URLs and key names, HTTP parser, and `ComputerUseService` (one request in, one response out, with every check).

macOS: `ComputerUseServer` (Network.framework socket), `MacComputerUseBackend` (runs the tools), `ComputerUseModule` (lifetime, permissions, emergency stop), `ComputerUseCard` (settings UI). For LAN mode: `ComputerUseTLS` (certificate and key in the Keychain), `ComputerUseCertificate` (builds the X.509 DER), `ComputerUseLAN` (private IPs, sleep prevention, Bonjour name, switches).

## How a request is handled (every step fails closed)
service running? (else 503) → path is `/mcp` (else 404) → client address allowed for the mode? (else 403) → Host/Origin allowed? (else 403; blocks DNS rebinding and cross-site browser calls) → client locked out? (429) → Bearer key valid? (401) → per-client request rate → per-key request rate → method is POST (else 405) → JSON-RPC → emergency stop → **tool group switch** → run the tool (one at a time).

- Missing, wrong or revoked key: always the same 401 body (`WWW-Authenticate: Bearer`). 5 failures within 60 seconds lock that client out for 60 seconds (429); while locked, even a correct key is refused. Failures are counted per client address, so on a LAN one computer being locked out does not affect the others. Behind a tunnel process on this Mac every caller shares the loopback address, so they are locked out together (an accepted trade-off).
- Rate limits: a request has to pass both a per-client limit and a per-key limit, 240 requests per minute each. The key limit is shared by all clients using that key. The tables are capped at 1024 entries (the least recently active go first).
- Client addresses are normalised (`::ffff:192.168.0.9`, upper/lower case, zone id and brackets all become one spelling), so changing the notation cannot dodge a lockout or a limit.
- Supported protocol versions: `2025-06-18`, `2025-03-26`, `2024-11-05`. `tools/list` lists only the tools of the groups that are switched on (and nothing while the emergency stop is active).
- The answer is a single JSON response (one request per connection, `Connection: close`). SSE, sessions and chunked bodies are not supported. Headers are limited to 16 KB and bodies to 1 MB. `Expect: 100-continue` is ignored (the client waits a moment, then sends the body).

## API keys
- 32 random bytes, shown as `nccu_` + base64url (43 characters). The key is shown in a dialog **once**, when it is made; if you copy it, the clipboard is cleared after 60 seconds.
- Only the SHA-256 hash is stored, in `~/Library/Application Support/NachoCombo/computer-use-keys.json` (mode 0600, folder 0700). `settings.json` holds nothing about keys. (A hash file instead of the Keychain: a hash is not a secret, and it had to be testable on Linux.) A key is checked against every stored hash with a constant-time comparison.
- Each key has a label (up to 40 characters). At most 8 keys at a time. Revoking takes effect at once. Reissuing replaces a key (the old key stops working at once, the label stays). The last-used time is saved at most once a minute.
- If the key file is unreadable, **all keys become invalid** (a copy is kept as `.corrupt`).

## Tool groups (all off by default, one switch per group)
- Screen: `screen_list_displays`, `screen_capture` (display, window or region; PNG; maximum width 1568 by default, adjustable from 64 to 4096)
- Apps and windows: `app_list`, `app_open`, `app_activate`, `app_quit`, `window_list`, `window_set_frame`, `window_minimize`
- Input: `mouse_move`, `mouse_click`, `mouse_drag`, `mouse_scroll`, `key_press`, `type_text` (up to 4000 characters)
- Clipboard: `clipboard_read`, `clipboard_write`
- Open: `open_url` (http, https and mailto only), `open_file` (absolute path; file types that run code or install things are refused, for example `.app`, `.pkg`, `.dmg`, `.command`, `.sh`, `.scpt`, `.workflow`, `.jar`, `.webloc`)
- System info: `system_info` (macOS version, model, uptime, memory, CPU cores, battery, output volume), `process_list` (pid and name only, no arguments)
- **High risk (separate switches; switching one on asks for confirmation):** `applescript_run`, `shell_run`, `file_read` / `file_write`, `process_kill`
  - Files: the home folder's `.ssh`, `.gnupg`, `.aws`, `Library/Keychains` and this app's own folder can be neither read nor written. Writing is allowed only under the home folder and `/tmp`, and never to shell start-up files, LaunchAgents, LaunchDaemons, Preferences or the TCC folder. Symlinks are resolved and the real path is checked again. Reads are limited to 256 KB, writes to 1 MB.
  - **AppleScript and shell can get around each other and around the file limits** (`do shell script`, and so on). Switching either one on hands over practically everything you can do as this user, which is why the page warns about it.
  - Shell: `/bin/zsh -c`, timeout 1 to 120 seconds (30 by default), output limited to 64 KB. On timeout only zsh gets TERM, then KILL; grandchild processes may survive.
  - `process_kill`: TERM (default), KILL, INT or HUP; never pid 0 or 1 and never Nacho Combo itself.

## Permissions
macOS permissions are requested **only when a tool group that needs them is switched on**: Screen needs Screen Recording; Apps and windows and Input need Accessibility; AppleScript needs Automation. If any is missing, the server is not opened. The gadget shows that a permission is needed, which one, and buttons to open System Settings and to check again (no workaround). Restoring the state at app launch and a plain re-check never show a permission dialog. Automation cannot be checked beforehand, so macOS asks per app on first use. Rebuilding or re-signing the app can invalidate a permission (the same as for the other gadgets).

## Emergency stop
`⌃⌥⌘.` or the button on the page: every call is refused at once, a running shell command is ended and the gadget is switched off (and saved as off). If the shortcut cannot be registered (a conflict), the server is not opened.

## Call log
The last 200 calls are kept in memory: tool name, time, key label, whether the tool is high risk and the outcome (ok, error or denied). Input text, arguments, screens and results are not recorded. Keys are not recorded anywhere.

## Known limits and differences from the plan
- **ScreenCaptureKit is not used (postponed).** The plan said "ScreenCaptureKit on 12.3 and later"; that is not implemented. Every macOS version uses `CGDisplayCreateImage` / `CGWindowListCreateImage` (the same calls Capture Float uses). Reason: linking the framework can stop the whole app from launching on macOS 12.0 to 12.2, and without a Mac there was no way to check. These calls are blocked when building with the macOS 15 SDK (Capture Float has the same issue); CI builds on `macos-15`, so a compile result will show it. To be decided once testing on a Mac is possible.
- Brightness cannot be read (no public API). Volume is only available when the default output device has a volume control.
- Windows are addressed by `pid` + `windowIndex` (the accessibility window order). The `index` in `window_list` is the CG window order and can differ for some apps; check the returned `frame`.
- The default is loopback only (`listenMode` = `localOnly`). Other computers on the same LAN: see [LAN mode](#lan-mode-core). A tunnel host name has to be added to `allowedHosts` (in `settings.json`) to pass the Host check. Tunnels are out of scope for now.
- **Not wired in yet:** in this tree, the macOS files are not yet connected to `AppDelegate` and the settings window (the existing per-gadget switches have no Computer Use case), and the page's labels, error texts, the certificate name, the Keychain label and the MCP `instructions` string are still the older Korean text. Both need doing before the gadget can be tried in the app.

## LAN mode (Core)
Other computers on the same local network connect with a key. **Off by default** (`localOnly`); it is on only when the user turns it on. The Core only makes the decisions; the socket, the TLS and the UI are on the macOS side.
- `ComputerUseListenMode { localOnly, lan }` → `ComputerUseSettings.listenMode`. A missing, unknown or wrongly typed value is read as `localOnly` (the settings file as a whole still loads). Settings written before LAN mode existed open as `localOnly`. `bindAddress` is still forced to a loopback address.
- `ComputerUseSettings.effectiveBindAddress`: `localOnly` = `127.0.0.1`, `lan` = `0.0.0.0` (`lanBindAddress`). `requiresTLS` is true in `lan`: LAN mode is never opened as plain HTTP.
- `ComputerUseNetworkPolicy.isPrivateAddress(String)`: 10/8, 172.16/12, 192.168/16, 169.254/16, fc00::/7, fe80::/10, 127/8 and ::1. IPv4-mapped IPv6 is judged by the IPv4 inside; brackets and `%zone` are accepted. Malformed text (a leading zero as in `010.0.0.1`, octal or hex notation, spaces, an attached port, and so on) is not private. 100.64/10 (CGNAT, Tailscale) is not private.
- `ComputerUseNetworkPolicy.isRemoteAddressAllowed(clientID, config)`: `localOnly` = loopback clients only, `lan` = private-range clients only. Public addresses and unparsable ones ("unknown") are refused in both modes. The service answers 403 **before the key check**, so an outsider gets no 401 hint and no failure is recorded.
- `ComputerUseNetworkPolicy.isHostAllowed(hostHeader, config)`: `localOnly` = localhost, 127.0.0.1, [::1] and `allowedHosts`. `lan` adds private IP literals, `*.local` (proper DNS labels only) and `localhost`. Public IP literals and ordinary DNS names (`192.168.0.5.evil.com`, `10.0.0.1.nip.io`, the DNS-rebinding cases) are refused unless listed in `allowedHosts`. Userinfo (`a@b`), paths, an empty port and IPv6 without brackets are refused. The Origin header is checked with the same function.
- Service entry point: `ComputerUseService.handle(_:clientID:)` (the client ID is the peer IP as text). The old `handle(_:peer:)` is kept with the same meaning so existing code still compiles. `ComputerUseNetworkPolicy.normalizeClientID` merges notations of the same address.
- Per-client separation: the failure lockout (5 in 60 seconds → 60 seconds) is per client IP. Request rate: the per-client limit (240 per minute, injectable) **and** the per-key limit (240 per minute) must both pass; the key limit is shared by all clients.
- The TLS fingerprint (SHA-256, hex) is produced by the macOS side and shown in the UI; the Core is not involved.

## LAN mode (macOS and UI)
The sockets, TLS and screen that use the Core contract above. **Off by default**; on only when the user turns it on in the Computer Use page ("Who can connect").
- **Server** (`ComputerUseServer`): `localOnly` = as before (127.0.0.1 / ::1, plain HTTP). `lan` = every interface (no `requiredLocalEndpoint`, cellular excluded), opened **with TLS only**, TLS 1.2 or later. If the certificate cannot be made or read, the gadget shows an error and nothing is opened (no plain-HTTP fallback).
- **Remote address check:** as soon as a connection arrives (before the handshake) its remote IP is normalised with `normalizeClientID`, and the connection is dropped unless it passes `isPrivateAddress` (lan) or `isLoopbackAddress` (localOnly). The service repeats the same check (403) before the key check. At most 4 simultaneous connections per client and 16 in total. A connection that has not finished its request within 15 seconds (handshake included) is dropped.
- **clientID:** the normalised remote IP is passed to `service.handle(_:clientID:)`, so lockouts and rate limits are per client.
- **TLS certificate** (`ComputerUseTLS`): the first time LAN mode is opened, one self-signed ECDSA P-256 certificate is made (valid 10 years). Its **SAN** lists `localhost`, `127.0.0.1`, `::1`, this Mac's **private IPv4/IPv6 addresses** at that moment (fc00::/7 and fe80::/10 addresses on interfaces that have a private IPv4) and **`<LocalHostName>.local`**. The **private key lives only in the login Keychain** (`SecKeyCreateRandomKey`, permanent key) and is never written to a file, a log or the settings. The certificate is stored in the Keychain as `kSecClassCertificate` and read back together with its key through a `kSecClassIdentity` lookup. Fingerprint = SHA-256 of the certificate DER (Core `SHA256`), shown as `AB:CD:…`. **The certificate is never renewed silently when addresses change** (the fingerprint would change); instead the page reads the stored certificate's SAN and shows an orange warning when a current address or the `.local` name is missing, naming what is missing. "Regenerate certificate" deletes the key and certificate and makes a new one for the current addresses (the fingerprint changes and the server restarts). After that, the page shows the old and the new fingerprint and the list of addresses and names in the certificate.
- **Certificate DER** (`ComputerUseCertificate`): the Security framework has no public API to create certificates, so the DER is assembled by hand and only the signature comes from `SecKeyCreateSignature(.ecdsaSignatureMessageX962SHA256)`. A minimal reader for the SAN (`subjectAltNames`) is in the same file. It uses Foundation only, so it can be checked on Linux with openssl.
- **Page:** LAN switch (asks for confirmation when turned on, and lists any high-risk groups that are on) · red warning · connection URL `https://IP:port/mcp` (one line per private IPv4, with a copy button) · one status line · fingerprint (selectable and copyable) and PEM copy · regenerate certificate · client example (check the fingerprint with `openssl s_client`, then `curl -k`, with the key in `$NACHO_KEY`) · prevent sleep · Bonjour · firewall note with a button that opens settings. Long address lines are cut in the panel and shown in full in a tooltip.
- **Firewall:** if the macOS firewall is on, the first time LAN mode is opened macOS shows an "allow incoming connections" dialog. It has to be allowed before other computers can connect. The page explains this and has a button that opens `x-apple.systempreferences:com.apple.preference.security?Firewall`.
- **Prevent sleep** (optional, off by default): while the server is open it holds one `IOPMAssertion(PreventUserIdleSystemSleep)`, released when the gadget is turned off, when the mode changes and on emergency stop. It does not stop the display from sleeping, and a sleeping display cannot be captured.
- **Bonjour** (optional, off by default, LAN mode only): announces `_nacho-mcp._tcp` with the name "Nacho Combo (computer name)" and the port. No key or fingerprint goes into the TXT record.
- These two switches (prevent sleep, Bonjour) are not in the shared settings file but in `UserDefaults` (`computerUse.preventSleep`, `computerUse.advertiseBonjour`), because they change how this Mac behaves, not what the MCP service allows.
- **Trust on the client side:** the certificate is not trusted through a CA chain. (a) Fingerprint pinning: on the first connection compare the fingerprint with the page and pin that value. It stays the same when addresses change, as long as the certificate is not regenerated, so the client keeps working. (b) Host name verification: put the PEM from "Copy certificate (PEM)" in the trust list (`curl --cacert nacho.pem https://IP:port/mcp`); verification then passes while the address you connect to (a private IP or `name.local`) is in the SAN. If the address changed and is no longer in the SAN, (b) fails until the certificate is regenerated and (a) is unaffected.

## Tests
- `swift test` covers the Core (keys, rate limits, JSON-RPC, settings, tool catalog, policies, HTTP parser, the service, and the LAN address and Host policies). It runs in CI on Linux and macOS.
- The certificate DER builder and SAN reader (`ComputerUseCertificate.swift`, Foundation only) are meant to be checked with openssl: the certificate must be v3, `ecdsa-with-SHA256`, `prime256v1`, `CA:FALSE`, `serverAuth`, with the SAN (DNS names and IPs; duplicates and malformed entries dropped, zones removed) readable by `openssl x509 -text`; `openssl verify` must pass; included IPs and host names must pass `-verify_ip` / `-verify_hostname` and others must be refused; a TLS 1.2 handshake against `openssl s_server` must verify the right IP and host name and refuse a wrong IP; and the fingerprint seen in the handshake must equal the SHA-256 of the DER.
- The Keychain, `NWListener` and the UI only run on a Mac; for them there is only the compile check in CI.

## Real-Mac test checklist
When testing on a Mac is allowed, go in this order (if an earlier item fails, the later ones mean nothing). Use a **freshly built app** and a new key (Create key) for every item. If the pass criteria are not met, stop at that item and report the result as it is (do not rewrite it as a pass).

1. **Compile**: run `BUILD_MODE=swiftc UNIVERSAL=1 scripts/build-app.sh` (or the SwiftPM mode). *Pass:* exit code 0, no errors (warnings are fine), `build/NachoCombo.app` exists, `codesign -v` passes. `plutil -p` on `Info.plist` shows `NSLocalNetworkUsageDescription` and `NSBonjourServices=[_nacho-mcp._tcp]`. If type errors appear, the LAN code (Network/Security/IOKit/SystemConfiguration calls) is the first suspect.
2. **localOnly binding** (the default): Computer Use on, LAN switch off. *Pass:* `lsof -nP -iTCP:47653 -sTCP:LISTEN` shows only `127.0.0.1:47653` (no `*:47653`). On the same Mac `curl http://127.0.0.1:47653/mcp` gives 401 (no key), and `tools/list` with the right key gives 200. From another computer, `http://<Mac IP>:47653/mcp` is refused.
3. **LAN mode TLS binding**: LAN switch on (confirm in the dialog). *Pass:* the status shows it is running; `lsof` shows `*:47653` (all interfaces) in LISTEN; a plain `curl http://<Mac IP>:47653/mcp` gets a TLS error or an empty reply (no plain-HTTP response); `openssl s_client -connect <Mac IP>:47653 -tls1_1` fails and `-tls1_2` succeeds. The page shows at least one line `https://<private IP>:47653/mcp`, and its copy button puts that URL on the clipboard. If the certificate cannot be made, the status is an error and the port is not opened.
4. **Fingerprint check, then a call from another computer**: on another computer on the same LAN, follow the page's example. *Pass:* the output of `openssl s_client … | openssl x509 -noout -fingerprint -sha256` equals the fingerprint on the page character for character. When it does, `curl -k` (or `--cacert nacho.pem`) gets 200 for `tools/list` and only the tools of the groups that are on appear. The certificate SAN (`openssl x509 -text`) has the Mac's private IPv4/IPv6 addresses and `<name>.local`, and with `--cacert nacho.pem` both the IP and `name.local` pass host name verification. A wrong key gets 401; five wrong keys lock out only that computer (429, 60 seconds), while a correct call from another computer, or from the Mac itself, at the same time is not affected.
5. **Non-private clients are blocked**: this needs a non-private source, such as a computer with a 100.64/10 address (CGNAT, Tailscale) connecting to the Mac's tailnet IP, or a computer routed in through a non-private address. If only private sources are available, write this item down as "not done" (never as a pass). *Pass:* the connection is dropped before the TLS handshake (`openssl s_client` receives no certificate) or the answer is 403. A 401 is a failure (it means the request got as far as the key check). No entry appears in the call log.
6. **Port closes after OFF**: (a) Computer Use off, (b) LAN switch off (back to localOnly), (c) quit the app, each in turn. *Pass:* for (a) and (c) `lsof -iTCP:47653` shows nothing and `curl` from another computer is refused. For (b) `*:47653` becomes `127.0.0.1:47653` and another computer is refused. Open connections are dropped at once.
7. **Firewall dialog**: System Settings ▸ Network ▸ Firewall on, and no allow entry for this app (after `sudo /usr/libexec/ApplicationFirewall/socketfilterfw --remove <app path>`); turn LAN mode on for the first time. *Pass:* the "allow incoming connections" dialog appears, another computer cannot connect before it is allowed, and item 4 passes after it is allowed. The page's open-firewall-settings button opens the firewall screen (or Privacy & Security); if it does not, fix the link. If the macOS 15 local-network permission dialog appears, its reason text is in English.
8. **Keychain prompts**: the first time LAN mode is turned on, and again when it is turned on **after the app was rebuilt (re-signed)**. *Pass:* at first creation there is no Keychain password or access prompt, or just one, and the login Keychain has one key and certificate pair labelled for LAN TLS (for example `security find-identity -p ssl-server`). If a prompt appears after a rebuild, record what it says (the fingerprint must still be the same after allowing). After "Regenerate certificate" there is still exactly one pair, the fingerprint has changed, and the page shows the old and the new fingerprint. When the address changes (for example another Wi-Fi), the orange warning that the certificate must be regenerated appears with the missing addresses, and a client that pins the fingerprint (the `-k` method of item 4) keeps connecting until it is regenerated.
9. **Permission flow**: with Screen Recording, Accessibility and Automation all revoked, switch the tool groups on one at a time. *Pass:* only the permission the group needs is requested; if any is missing the page says a permission is needed, offers the button for that System Settings pane, and the port is not opened. After allowing, "check permissions again" opens the server (if a restart is needed, record that). Restoring state at app launch and a plain re-check show no permission dialog.
10. **Screenshot and input tools** (from the other computer of item 4): Screen group on → `screen_list_displays`, `screen_capture` (display, window, region). Input group on → `mouse_move`, `mouse_click`, `key_press`, `type_text`. *Pass:* the captured PNG opens and shows the right screen, and the mouse and key input really arrives. Switching a group off removes its tools from `tools/list` and refuses calls to them. The call log keeps only tool names and key names, never the typed content or screens.
11. **Prevent sleep**: with "keep the Mac awake while the server is on" selected, Computer Use on, the power adapter connected and idle sleep set short in the energy settings. *Pass:* `pmset -g assertions` lists a `PreventUserIdleSystemSleep` assertion whose reason says Nacho Combo's Computer Use server is on, and the Mac stays reachable from another computer after the idle time. The assertion disappears when the switch is turned off, when the gadget is turned off, on a mode change and on emergency stop. (A captured screen being blank when the display sleeps is a known limit.)
12. **Emergency stop**: with a client connected over LAN mode, press `⌃⌥⌘.` (and, separately, the page's emergency-stop button). *Pass:* a running shell command ends, every later call is refused at once, the gadget is saved as off and the port is closed (the criteria of item 6), and the sleep-prevention assertion is released. If registering the shortcut conflicts, the server does not open and the status says why.
13. **Bonjour** (optional): turn the Bonjour switch on (LAN mode). *Pass:* on another Mac `dns-sd -B _nacho-mcp._tcp` lists "Nacho Combo (name)", and neither the TXT record nor the name contains a key or fingerprint. It disappears after the switch is turned off or LAN mode is turned off.
